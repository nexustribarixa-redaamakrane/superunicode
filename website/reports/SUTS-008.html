SUTS-008 — SuperUnicode Source Code Handling

The eighth SuperUnicode Technical Specification: a zero-allocation, single-pass engine for source code safety screening in the OpenWindows microkernel.

SUTS-008 (SUSCH) is the eighth SuperUnicode Technical Specification and a core kernel primitive of the OpenWindows microkernel. It establishes a binary-compiled, zero-allocation architecture for source code handling — compiling a codepoint to a fixed-size safety attribute record, validating a whole identifier token in a single pass, and reporting homoglyph, mixed-script, and cross-zone findings as advisory bitmaps — replacing the text-scanning pipeline of Unicode’s UTS #55 (a maintainer-mode lexer, a set of regular-expression-style filters over identifier characters, and a per-file diagnostic report) with fixed-size, byte-aligned memory layouts optimized for O(1) kernel execution.

Why not a text scanner

  • Token validator vs. file scanner — UTS #55 must decide where an identifier begins and ends inside arbitrary text, so it carries a maintainer-mode lexer and needs a source line for every diagnostic; SUSCH is handed the codepoint stream of one identifier, already delimited, and never re-lexes it.
  • Verdict and bitmap vs. diagnostic report — a linter emits prose with line numbers and ranges for a human reader; SUSCH emits a boolean verdict, a closed outcome code, and a packed advisory word, because the consumer is a compiler front end, a kernel script engine, or a CI gate.
  • Compiled tables vs. runtime filters — UTS #55 loads properties and confusables data into memory and runs a filter over the text; SUSCH answers every per-codepoint question by a bounded binary search over an immutable static table, with no file reads and no per-file setup.
  • Zero allocation vs. per-line buffers — a user-space linter allocates per-line buffers, per-match records, and a report tree; SUSCH allocates nothing at all, and holds a fixed number of registers whatever the token’s length.

The division of labour follows UTS #55: a directional control or an invisible character makes a token invalid, while a confusable, a mixed-script chunk, and a chunk that crosses the Bridge boundary are warnings that never change the verdict. A legitimate Greek or Cyrillic identifier must still compile — the finding is what a linter or a CI gate acts on, not a rejection.

Dual-layer architecture

Layer Role
SUCD — offline reference Full human-readable confusables manifests, identifier-status tables, Default_Ignorable_Code_Point inventories, and directional-formatting-character inventories for user-space compilers, linters, IDEs, and developer toolchains
SUSCH — runtime kernel Immutable, byte-packed binary lookup tables (the class, skeleton, identifier, script, and case tables) queried by the kernel in O(1), with a 12-byte attribute record per codepoint

The seeding brief for this specification named its offline reference layer “SUCD — SUAS-014”. That is stale: in this corpus SUCD is the SuperUnicode Character Database (SUAS-012), while SUAS-014 is SUVTL, the SuperUnicode Version and Licensing Table, which has nothing to do with character data. SUSCH therefore names SUCD (SUAS-012) as its reference layer. The house prefix SUSCH_* and the entry points suts_susch_init_engine, suts_susch_get_attributes, and suts_susch_validate_token_stream are preserved verbatim.

The compiled attribute

A compiled source attribute is a fixed 12-byte entry binding a 31-bit codepoint to its packed security mask, its coarse script classification, and its three-state identifier verdict; the sketch’s field layout is preserved unchanged. The four sketched flags keep bits 0–3, the derived flags occupy bits 4–12, and the query is total over the whole 31-bit address space: an unclassified codepoint is answered by the algorithmic default rather than by a lookup failure.

#define SUSCH_FLAG_VALID_IDENTIFIER (1U << 0)
#define SUSCH_FLAG_BIDI_CONTROL (1U << 1)
#define SUSCH_FLAG_INVISIBLE (1U << 2)
#define SUSCH_FLAG_HOMOGLYPH_RISK (1U << 3)

typedef struct {
uint32_t codepoint; /* Raw 31-bit SuperUnicode codepoint */
uint32_t security_mask; /* Packed source code safety attributes */
uint16_t script_category; /* Associated script classification */
uint8_t identifier_status; /* Allowed, Restricted, or Disallowed */
uint8_t reserved; /* must be zero */
} susch_source_attr_t; /* exactly 12 bytes */

Identifier admission

Every codepoint carries a three-state admission verdict: Allowed (admissible with no caveat), Restricted (admissible, but carrying a caveat the caller should see — a confusable prototype, a joining control, a neography character), and Disallowed (never identifier material). The positional rule is separate: suts_susch_is_identifier_start and suts_susch_is_identifier_continue decide whether a codepoint may open or extend an identifier, so a decimal digit continues happily and never starts.

Identifier chunks

Chunk boundaries are the camel, hat, and snake boundaries of UTS #55 §5.1.2.1, expressed in terms of compiled case classes rather than runtime property lookups. A combining mark never forms a chunk of its own: it belongs to the letter it follows.

Token Chunks Rule
HTTPRequest HTTP | Request HAT before R
TypeII Type | II CAMEL before I
OCaml O | Caml HAT before C
my_variable my | _ | variable SNAKE on both sides
abc abc no rule fires

The hat rule needs to see the codepoint after the one it applies to, so the boundary decision is taken with a one-codepoint lookahead. The engine holds two chunk-significant codepoints in registers and never re-reads the stream: the pass stays linear.

The RNUR neography carve-out

SUSCH does not invent a second plane taxonomy: suts_susch_zone_of classifies a codepoint into the SUCD / SSP planes with the RNUR carve-out made explicit. Only the Bridge (0x00000000–0x0010FFFF) and the RNUR neography zone (0x00160000–0x0016FFFF) carry source text; the Control Plane, the trap slots, the Sentinel, and ExtSUCS are never source material. Within the RNUR, every 0x100-aligned block is one neography set: offsets 0x00–0x5F are letter positions, 0x60–0x7F are continuation-only, and 0x80–0xFF are symbol positions that may never appear in an identifier. A neography character is Restricted rather than Allowed, because the shipped table cannot vouch for a profile it does not carry.

Outcome codes

Code Meaning
SUSCH_TOKEN_OK the stream is a valid identifier
SUSCH_TOKEN_ERR_NULL a NULL stream with a non-zero length
SUSCH_TOKEN_ERR_EMPTY a zero-length identifier
SUSCH_TOKEN_ERR_ILLEGAL_ZONE a trap slot, the Sentinel, the SCP, or ExtSUCS
SUSCH_TOKEN_ERR_BIDI_CONTROL a directional formatting character
SUSCH_TOKEN_ERR_INVISIBLE a zero-width or invisible character
SUSCH_TOKEN_ERR_LINE_BREAK a line terminator inside the token
SUSCH_TOKEN_ERR_INVALID_START the first codepoint may not start an identifier
SUSCH_TOKEN_ERR_INVALID_CONTINUE a later codepoint may not continue one

The four advisory bits — SUSCH_WARN_HOMOGLYPH, SUSCH_WARN_MIXED_SCRIPT, SUSCH_WARN_CROSS_ZONE, and SUSCH_WARN_RESTRICTED — never change the verdict. The two joining controls U+200C and U+200D are the one exception to the invisible rule: UTS #55 §5.1.3 permits them under contextual restriction, so they stay admissible and are reported through the advisory channel instead.

Modular optional compliance

SUSCH is a modular specification. The architectural contract — the attribute layout, the compiled tables, the chunk grammar, the defect / advisory split — is mandatory for an implementation that claims SUSCH support; but a minimal kernel MAY omit the module entirely, because core operating system primitives, file paths, and kernel IPC channels need strict text safety rather than a source code linter. An implementation that omits SUSCH obtains the equivalent guarantees from the user-space reference layer (SUCD) directly.
