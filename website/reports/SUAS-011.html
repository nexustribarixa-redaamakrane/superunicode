SUAS-011 — System Character Manifest & Schema

The structural counterpart of UAX #42: a flat, tab-delimited manifest grammar that compiles straight into immutable kernel tables — no DOM, no heap, no second pass (a UAX #42 analog).

SUAS-011 (SCMS) is the eleventh SuperUnicode Architecture Standard and the structural counterpart of UAX #42, the Unicode Character Database in XML. It defines the exact grammar and field-mapping rules by which an offline character manifest is written, validated, and compiled into the immutable binary lookup tables the OpenWindows kernel embeds.

UAX #42 describes the character database as an XML schema, and that choice is expensive in a way that is structural rather than incidental. XML is hierarchical, so a record has no fixed size and no fixed offset; a parser must build a tree, and building a tree means allocating; a schema validator is a general-purpose engine, so its cost is unbounded by anything the database knows; and nothing in the result is binary-mappable, so a kernel must re-encode it a second time before the first lookup can happen. A database compiled through UAX #42 costs a DOM, a heap, and two full passes before a single query returns.

Why line-oriented

SCMS rejects hierarchical markup precisely because it wants binary mappability. A manifest is a stream of lines; a record is exactly six tab-delimited fields in a fixed order, each of a known and bounded type; a directive is a name and a value. One record line corresponds to one kernel table entry, in order, with no re-encoding step and no intermediate tree. Build tooling parses a manifest in a single linear pass over zero-allocation streaming buffers, and a manifest that does not validate is never compiled.

The record grammar

record := start TAB end TAB radical TAB strokes TAB flags TAB weight
# Column Form Bounds
0 start U+ + 1–8 hex admissible
1 end U+ + 1–8 hex admissible, ≥ start
2 radical decimal 0 … 214 (Kangxi)
3 strokes decimal 0 … 255
4 flags 0x + 1–4 hex 0 … 0xFFFF
5 weight decimal 0 … 0xFFFFFFFF

A single codepoint is expressed as end == start, and such a record is binary-aligned: it maps to exactly one kernel table slot rather than a run the tool must expand. is_binary_aligned is the compilation decision the parse descriptor exists to carry.

The record descriptor

The descriptor reports structure, not payload: the range resolved, how many columns were found, and whether the record maps to a single table slot. A compiler walks the payload columns itself through suas_scms_field_at, which decodes column n on demand. This keeps the descriptor fixed-size and keeps one code path responsible for each field’s bounds.

typedef struct {
sucs_ex_char_t start_codepoint;
sucs_ex_char_t end_codepoint; /* equal to start for one codepoint */
uint16_t field_count; /* fields actually found, not expected */
bool is_binary_aligned; /* true iff the record is one codepoint */
} scms_record_descriptor_t;

Codepoints are widened to the 64-bit ExtSUCS type sucs_ex_char_t so an RNUR neography logograph survives the round trip, even though the grammar currently caps U+ at eight hex digits.

Admissibility: the interior is the point

Range validation runs in a fixed order so the reported outcome names the first thing that is wrong — ordering, then the endpoints, then the interior, then the span ceiling. The interior check is the step a naive implementation omits, and it is the one that matters:

A range from U+10FFFF to U+00120000 has two perfectly admissible endpoints and swallows the entire System Control Plane in between. A manifest range is a promise that every codepoint it covers is data; a range is admissible only when that promise holds throughout.

This is the SCP invariance that SIP and SCSS enforce on live codepoint queries, applied to the data at rest — so a malformed manifest cannot smuggle a Control Plane codepoint, a trap slot, or the Sentinel into the image in the first place. RNUR neography (0x160000–0x16FFFF) is fully admissible and is reported by the plane mask as both NATIVE and RNUR.

The streaming reader

A manifest is read through a caller-allocated scms_manifest_state_t — typically on the stack — so an entire database can be validated with no allocation at all. The reader accumulates counts and the observed plane mask, attributes the first error to its 1–based line number, and on close requires a %manifest directive, at least one record, no failed line, and agreement with a declared %records total. A separate cross-check requires every plane the records touched to appear in the declared %planes mask.

The SSRE linkage gate

A manifest is meaningless in isolation: it exists to feed a target schema, and that schema is itself a registered specification. SCMS validates the manifest’s structure; SUAS-010 (SSRE) validates that the destination exists and is satisfiable. Both must hold before a blob is embedded.

Case Result
Schema unregistered Refused — a blob nobody can resolve must not be embedded
mandatory asserted against an optional SUTS data spec Refused — a mislabelled architectural claim
Version floor above the registered version Refused — schema misalignment

Named failures

Every rejection carries its own outcome code, because a compiler that rejects a database must be able to say exactly why — a silently truncated radical reaching a kernel table is the failure this standard exists to prevent. The reference suite pins each violation to its own code.

Numbering note

The seeding sketch was labelled SUAS-013; it is registered as SUAS-011, the number immediately after SUAS-010 (SSRE), which keeps the SUAS series contiguous with no reserved gaps. SUAS-013 was unallocated when this standard was written; it now names SISR.

As with SIP, SSRE, and SCSS, the brief named the offline reference layer “SUCA”; in this corpus SUCA is already the SuperUnicode Collation Algorithm (SUTS-001), so SCMS names SUCD as the character database it holds.

Reference implementation: include/suas/suas_scms.h + src/suas/suas_scms.c (freestanding C99, no heap), registered in suas_static and in the SSRE registry as a MANDATORY specification.
