SUTS-009 — SuperUnicode Link Detection & Formatting

The ninth SuperUnicode Technical Specification: a zero-allocation, byte-packed engine for URL and email detection in the OpenWindows microkernel.

SUTS-009 (SULDF) is the ninth SuperUnicode Technical Specification and a core kernel primitive of the OpenWindows microkernel. It establishes a binary-compiled, zero-allocation architecture for link detection — compiling a codepoint to its Link_Term, Link_Bracket, and Link_Email attributes, scanning a codepoint stream for URLs and email addresses in a single pass, and serializing a URL Part with minimal percent escaping — replacing the text-scanning pipeline of Unicode’s UTS #58 (property files, a candidate finder, a regex-driven termination algorithm) with fixed-size, byte-aligned memory layouts optimized for O(1) kernel execution.

Why not a text scanner

  • Codepoint stream vs. document — UTS #58 is written against the text of a document and its surrounding markup; SULDF is handed the codepoint sequence a terminal emulator, chat client, or mail reader already holds, and never re-lexes a byte index.
  • Compiled tables vs. runtime property files — UTS #58 loads LinkTerm.txt, LinkBracket.txt, and LinkEmail.txt and interprets them with a regex; SULDF embeds the merged, sorted, non-overlapping ranges directly in the image and probes them with a bounded binary search.
  • Zero allocation vs. candidate buffers — a user-space linkifier allocates candidate buffers, per-match records, and a report tree; SULDF allocates nothing at all, and holds one fixed 125-entry bracket stack on the scanner’s own frame.
  • A verdict vs. a report — UTS #58 reports match offsets for a human or a renderer; SULDF returns a half-open codepoint span and a kind, because the consumer is a kernel text primitive.

Dual-layer architecture

Layer Role
SUCD — offline reference The human-readable LinkTerm.txt, LinkBracket.txt, and LinkEmail.txt inventories (Unicode 18.0.0) for user-space linkifiers, validators, and toolchains
SULDF — runtime kernel Immutable, byte-packed binary range tables (term, email, bracket) queried by the kernel in O(1), with a 12-byte link attribute record per codepoint

The seeding sketch preserved the house prefix SULDF_*, the entry points suts_suldf_init_engine, suts_suldf_get_attributes, and suts_suldf_scan_stream, the four sketch flags (SCHEME_CHAR, DOMAIN_CHAR, PATH_CHAR, EMAIL_DELIM), and the 12-byte attribute layout. All are preserved verbatim. Like SIP, SSRE, SUCD, SIDN, SUEPS, and SUSCH, SULDF names SUCD (SUAS-012) as its reference layer.

The compiled attribute

A compiled link attribute is a fixed 12-byte entry binding a 31-bit codepoint to its packed attribute word, its Link_Term category, and its Link_Bracket role; the sketch’s field layout is preserved unchanged. The four sketched flags keep bits 0–3, the derived flags occupy bits 4–12, and the query is total over the whole 31-bit address space: an unlisted codepoint is answered by the algorithmic default Link_Term = Hard rather than by a lookup failure.

#define SULDF_FLAG_SCHEME_CHAR (1U << 0)
#define SULDF_FLAG_DOMAIN_CHAR (1U << 1)
#define SULDF_FLAG_PATH_CHAR (1U << 2)
#define SULDF_FLAG_EMAIL_DELIM (1U << 3)

typedef struct {
uint32_t codepoint; /* Raw 31-bit SuperUnicode codepoint */
uint32_t link_mask; /* Packed link-detection attributes */
uint16_t term_class; /* Link_Term: Include / Hard / Soft / Close / Open */
uint8_t bracket_class; /* Link_Bracket: None / Open / Close */
uint8_t reserved; /* must be zero */
} suldf_link_attr_t; /* exactly 12 bytes */

Link_Term

A compiled attribute binds a codepoint to its Link_Term category and its Link_Bracket role; a compiled span carries its kind and half-open codepoint offsets. The sketch’s field layout is preserved unchanged, and the query is total over the whole 31-bit address space: an unlisted codepoint is answered by the algorithmic default Hard rather than by a lookup failure.

Category Meaning
Include keeps a link going
Hard always terminates; the algorithmic default for unlisted codepoints
Soft terminates only if the next character does not continue the link
Close a closing bracket; terminates unless it matches an open bracket on the stack
Open an opening bracket; pushed and kept

Termination and the bracket stack

The termination algorithm walks the codepoints after a host in one pass with backup. An Open bracket is pushed on a fixed 125-entry stack; a Close bracket is popped only if it matches the top of the stack, and terminates the link otherwise. A Part’s ClearStackOpen set is checked before its Terminator, so a bracket opened in the Path is forgotten at the Query initiator. A Hard codepoint terminates, and a Soft codepoint that is not followed by Include material is removed from the link. The bounded stack is a security property: a hostile stream cannot drive an allocation or an unbounded walk.

URL initiation and email detection

A URL is initiated by an explicit http:// or https:// scheme or as a bare domain of at least two labels. The host parser admits labels whose ends are not hyphen edges, accepts the IDNA dot equivalents (U+002E, U+3002, U+FF0E, U+FF61), parses an optional :port, and rejects an empty label. Userinfo is rejected: a scheme://user@host is not a link.

An email detection begins at an @, walks backward over the Link_Email local-part (rejecting a leading, trailing, or consecutive dot), and parses the domain with the same host parser. A preceding mailto: is included. The Link_Email table is also what answers the domain-label question, so a link can never span a codepoint that may not appear in a host.

Minimal escaping and quoting

The formatter serializes one URL Part’s interior with the UTS #58 minimal-escaping algorithm: the Part’s Terminator and ClearStackOpen sets drive which literal characters must be percent-escaped. Non-ASCII bytes use SUTF-8 (SUTR-1), so a codepoint above the Bridge is escaped by its full byte sequence. The return value follows the snprintf convention. Email local-parts that are not valid under Link_Email are wrapped in ASCII double quotes with the two RFC 5322 specials backslash-escaped.

Security considerations

  • No userinfo — a scheme://user@host is not a link, so a renderer cannot present an attacker-controlled userinfo string as part of a trusted host.
  • No empty or hyphen-edged labels — a host that cannot be a host is rejected rather than linked.
  • Bounded brackets — the open-bracket stack is a fixed 125 entries, so a hostile stream cannot drive unbounded work.
  • Bidi controls are visible — suts_suldf_is_bidi_control identifies the explicit controls, implicit marks, and isolate initiators, because a link whose displayed text disagrees with its codepoints is a spoof, not a link.

The RNUR neography carve-out

Unlike a standards-conformant linkifier restricted to the Unicode Compatibility Bridge, SULDF admits the Native & Neography Plane as link material. A Native or neography codepoint in a Path, Query, or Fragment is an Include character and is retained verbatim by the minimal-escaping formatter, so a custom script’s URL stays readable instead of being silently percent-encoded. Only the Bridge (0x00000000–0x0010FFFF), the Native plane, and the RNUR neography carve-out (0x00160000–0x0016FFFF) carry link material; the Control Plane, the trap slots, the Sentinel, and ExtSUCS never do.

Modular optional compliance

SULDF is a modular specification. The architectural contract — the attribute layout, the compiled tables, the termination algorithm, the escape and quote forms — is mandatory for an implementation that claims SULDF support; but a minimal kernel MAY omit the module entirely, because core operating system text primitives need strict link boundaries, not a hyperlink renderer. An implementation that omits SULDF obtains the equivalent guarantees from the user-space reference layer (SUCD) directly.
