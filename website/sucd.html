The Machine-Instruction Database

SUCD 0.1.0 — the authoritative data behind Base SUCS and ExtSUCS.

The SuperUnicode Data Collection (SUCD) plays the role the Unicode Character Database plays for Unicode: machine-readable files that define every codepoint, block, property, name and mapping. It is versioned exactly like unicode.org/Public:

/Public/0.1.0/
sucd/ core inventory: SUCSData, Blocks, Props, Derived, auxiliary
sudat/ unidata: assignments, control/, bancodes/
names/ NamesList, NameAliases
sources/ provenance
collation/ SUCA ordering
sutf/ SUTF8/16/32 framing tables
charts/ code charts
mappings/ UNICODE, LEGACY, OBSOLETE
partitions/ partition policy (OWFS or USFS)

What ships in 0.1.0

sucd — core inventory

SUCSData.txt (codepoint → name → type), Blocks.txt, Props/, Derived/ and auxiliary/.

sudat — unidata

The control plane: control/SCP.txt, Traps.txt, Sentinel.txt, plus the four BANcode Registry blocks under bancodes/.

mappings

UNICODE.txt documents the permanent 1:1 bridge across 0x000000–0x10FFFF.

partitions

The policy that Base partitions may be OWFS or USFS while plugin partitions must be OWFS.

Browse the data

The full, versioned trees live in the repositories and are listed live by the Unicode repository listing:

  • modules/unicode — the Base SUCS module (core, Public/)
  • modules/unicode-extended — ExtSUCS + plugin subsystem + SDK
  • modules/sutf — SUCS UTF-8/16/32 framing reference
  • modules/extsutf — Extended transport (vector, vsutf, esutf)
  • modules/unified — the one-TU test that compiles every public header

Security

Release archives are attested with the same checksum family as plugin blobs — crc32c and fletcher64 — recorded under /Public/security/.

OpenWindows Storage. The filesystem layer behind the partition policy is specified by OpenWindows Storage (OWFS via libowfs.a, USFS via libusfs.a): OWFS data begins at drive offset 0x10000, integrity is CRC32c + Fletcher-64, and the identity layer is htl_device_t/ow_sec with optional ChaCha20 data-at-rest encryption.
